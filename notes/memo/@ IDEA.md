**④ "라그랑주 식에서 모델별로 λ를 따로 쓸 수 있냐, high만 더 엄격하게?"** — **네, 되고 수학적으로도 안전합니다.** 증명을 짧게 드리면:

```
지금: EV(m) = q̂(m) − λ · ĉ(m) / light_total          (λ 하나)
변경: EV(m) = q̂(m) − λ · r[m] · ĉ(m) / light_total    (r[m] = 모델별 고정 위험계수, r[light]=1)
```

`r[m]`을 **미리 정한 상수**로만 쓰면(이분탐색 중엔 안 바뀜), 교본 08장의 단조성 증명이 그대로 성립합니다 — `λ`가 커질 때 `r[m]·ĉ(m)`도 같이 커지니까 "비쌀수록 더 크게 깎인다"가 유지되고, 이분탐색이 여전히 됩니다. 구현은 `hash_regex.select_models`의 `choose()` 안 한 줄만 바꾸면 됩니다: `costs[candidate]` → `RISK_MULTIPLIER[candidate] * costs[candidate]`. `r[axk1-think]`를 1보다 크게(예: 1.5) 잡으면 "k1은 실제 비용보다 더 비싸다고 치고 계산"하는 효과가 나서, 정확히 님이 원하는 "high를 엄격하게" 가 됩니다. `r[m]` 값 자체는 나중에 부트스트랩 실험(교본 10 §5)으로 데이터 기반으로 정하면 됩니다.

@ (반내림 기작은 어차피 이거랑 같은 도메인이라 복수 개의 람다로 통일하면 될듯.)

=> **이 한 줄 대답이 너무 짧았어서 왜 같은 도메인인지 풀어서 설명할게요.** "애매하면 싼 쪽으로 반내림"이라는 규칙은 수학적으로 "비싼 모델이 이기려면 EV가 확실히 더 커야 한다"는 **문턱(threshold)을 하나 요구하는 것**과 같습니다. `risk_multiplier[high] > 1`을 곱하면 정확히 이 효과가 납니다 — 비싼 모델의 EV가 `r[high]`배만큼 깎이니까, 근소한 차이(애매한 경우)로는 못 이기고 확실히 나을 때만 선택됩니다. 즉 "반내림 로직을 따로 짤" 필요 없이, **risk_multiplier 값 자체가 이미 그 반내림 문턱의 크기를 조절하는 손잡이**입니다(`r[high]`가 클수록 더 엄격하게 반내림). 님이 원했던 "올림은 막고 반내림만"도 이미 만족됩니다 — `r[light]=1`로 고정해뒀으니 light 방향으로 깎이는 일은 없거든요.

### ① 가중치 기반 수식 / 룰 기반 (Rule-based Scoring)

- **방식:** 쿼리의 길이, 키워드(예: "코드 작성", "번역", "요약"), 정규표현식, 복잡도 어휘 사전 등을 이용해 << 쿼리의 난이도 점수를 계산 >> 합니다.
    
- **특징:** 구현이 가장 단순하며 속도가 압도적으로 빠르고 리소스를 거의 쓰지 않습니다. << 그러나 문맥(Context)이나 뉘앙스를 파악하는 데 한계 >> 가 있습니다. => 당연하지... reg ex, 어휘사전, 길이, 키워드 정도로 되는거면 쉽지않을거임. 
    
### ② 전통적 머신러닝 분류기 (ML Classifier)

- **방식:** TF-IDF나 Bag-of-Words 같은 경량 텍스트 텍스트 피처 추출기를 거친 뒤, **Logistic Regression, SVM, Random Forest, XGBoost** 등의 전통적 ML 모델로 특정 쿼리를 어떤 LLM으로 보낼지 분류합니다.
    
- **특징:** 로컬 CPU 수준에서도 수 밀리초(ms) 단위로 동작하며, 학습 데이터를 통해 쿼리 유형별 최적의 모델 매핑 감각을 익힐 수 있습니다.
    

### ③ 임베딩 기반 코사인 유사도 / k-NN 검색

- **방식:** 로컬에서 가볍게 돌릴 수 있는 소형 센텐스 임베딩 모델(예: `bge-small`, `all-MiniLM-L6-v2` 등)을 이용해 쿼리를 벡터화합니다. << 이후 미리 정의된 각 LLM의 "강점 영역 벡터 cluster" 또는 과거 데이터셋과 유사도를 측정하여 최선의 모델을 선택 >> 합니다.
    
- **특징:** 키워드가 직접 일치하지 않아도 <<의미적(Semantic) 복잡도>> 를 판단할 수 있어 성능이 높습니다. => 이거는 좀 어려울 가능성이 높음. ML의 한계처럼..
    

### ④ 소형 슬림 분류용 SLM (Small Language Model)

- **방식:** 쿼리 분류만을 전문으로 하도록 fine-tuning된 아주 작은 로컬 분류 모델(예: Bert-base, RoBERTa-tiny 등)을 사용합니다.
    
- **특징:** 문맥 이해도가 높고 "이 문제는 어떤 모델이 가장 잘 푸는가"를 고차원적으로 추론해낼 수 있습니다.

**1. 데이터 의존적이지 않은 규제 방식 — 있습니다, 이미 재료도 갖고 있어요.** 지금 grid search는 Dev 부트스트랩(별도 held-out 데이터)에 의존하는데, **모델 자기 자신의 out-of-fold 잔차 분산에서 직접 공식으로 뽑는 방법**이 있습니다. `train_router.py`가 smearing 계산할 때 이미 `cost_oof`(out-of-fold 예측)와 실제값의 잔차를 계산해두는데, 이 잔차의 표준편차를 모델별로 재서 `risk_multiplier[m] = exp(z · std(residual[m]))` 같은 공식(z는 신뢰수준 상수, 예: 95%면 1.645) 쓰면 **Dev를 전혀 안 보고 Train만으로** 원칙적인 risk_multiplier가 나옵니다. axk1-think가 잔차 분산이 제일 크니 자동으로 제일 큰 risk_multiplier를 받게 되고요. 이게 "독자적 모델의 성능 지표에서 사용 가능한가"에 대한 답 — 네, 가능하고 이미 있는 계산에서 한 줄 더 뽑으면 됩니다.

**2. 그리드를 더 넓게/촘촘하게 vs 과적합 — 님 직관이 정확히 맞습니다.** 그리드를 촘촘히 할수록 "Dev 880개+부트스트랩 300회에서 우연히 좋아 보이는 점"을 고를 위험(다중비교 문제)이 커집니다. 원칙적인 기준: 부트스트랩 추정치의 통계적 잡음 크기(K=300이면 초과확률 추정 표준오차가 대략 `sqrt(p(1-p)/300)` ≈ 1%대 확률에서 0.6%p 정도)보다 촘촘한 격자는 "다른 값"이 아니라 "잡음 차이"일 뿐이라 무의미합니다 — 즉 **격자를 무한정 촘촘히 하는 대신, 이 잡음 크기보다만 촘촘하면 충분하고 그 이상은 과적합**입니다. 더 나은 대안은 고정 리스트 대신 초과확률이 정확히 목표치(1%)에 닿는 지점을 **이분탐색으로 직접 찾는 것**(safety_ratio에 대해 초과확률이 대략 단조감소하니 가능) — 후보 몇 개 만이 아니라 정확한 경계를 바로 찾아서 다중비교 문제 자체가 줄어듭니다.

**"최종규제 강하게, 그 아래 규제 약하게"는 사실 이미 구현돼 있는 구조예요.** `safety_ratio`(전체 예산 상한 — 강한/최종 규제)와 `risk_multiplier`(모델별 선택 기준 — 약한/내부 규제)가 정확히 이 두 층입니다. "규제에 걸리면 cut하기 어렵다"고 걱정하신 부분도 이미 해결돼 있어요 — 이분탐색이 `safety_ratio` 상한을 넘으면 자동으로 penalty를 올려 선택을 다시 계산하니(그냥 뒤에서 잘라내는 게 아니라 처음부터 다시 계산), "cut"이 아니라 "재계산"이라 어색함이 없습니다. "몰아주기" 걱정도 근거가 약해요 — 매 문항마다 독립적으로 제일 가성비 좋은 모델을 고르는 구조라(argmax), 특정 모델에 강제로 몰리는 메커니즘 자체가 없습니다. 즉 이 아이디어는 이미 우리가 쓰고 있는 구조의 다른 표현이었던 셈입니다 — 새로 구현할 필요 없이, 지금 등급별 독립 탐색(진행 중)이 바로 이걸 등급마다 최적화하는 작업이에요.

## 첨삭에 대한 답 (냉정한 판정)

### 1번 — "어쩔 수 없는 느낌" 판단은 맞다. 다만 **한 번에 결판내는 실험**이 있다

보류가 합리적이지만, "정말 어쩔 수 없는지"를 **30분이면 증명하거나 반증**할 수 있다.

근거: score는 생성 2~4회의 **평균**이다(`num_generations`). 그러면
`gain = ax31평균 - light평균`에는 샘플링 잡음이 섞여 있고, 생성 횟수가
많을수록 잡음이 작다.

**결정적 실험**: 4회 생성 문항과 2회 생성 문항을 나눠서 각각 상관계수를 재본다.
- 4회 쪽 상관이 **뚜렷이 높으면** → 병목은 잡음이다. 특징을 아무리 개선해도
  못 넘는 천장이 있다는 뜻이고, 이 방향은 확실히 접어도 된다.
- 두 쪽이 **비슷하면** → 병목은 잡음이 아니라 특징이다. 그럼 다시 팔 가치가 있다.

지금은 "느낌"으로 접는 건데, 이 실험이면 **근거로** 접을 수 있다. 결과보고서에
쓰기에도 훨씬 강한 문장이 된다.

### 2번 — 방향 맞다. 그런데 **더 근본적인 개선**이 하나 숨어 있다

제안하신 다각도 분석(길이/단어/문장부호/반복성)은 타당하다. 다만 냉정하게 보면
지금 ridge가 266개 특징으로 **이미 그걸 하고 있고** 실제스케일 상관 0.46~0.62가
나온다. 특징 몇 개 더 얹는 걸로 크게 뛸지는 불확실하다.

**대신 구조적으로 잘못된 게 하나 있다**: 우리는 `cost`를 통째로 예측한다.
그런데 공식이

```
cost = fixed_cost + in_rate × input_tokens + out_rate × output_tokens
```

이고, **`input_tokens`는 프롬프트만 보면 라우팅 시점에 이미 알 수 있는 값**이다
(모르는 건 `output_tokens`뿐이다). 지금은 모델에게 "이미 아는 부분까지 같이
맞춰라"고 시키는 셈이라, 알 수 있는 걸 굳이 노이즈로 만들고 있다.

-> `output_tokens`만 타깃으로 예측하고, `input_tokens`는 계산해서 더하면
   예측해야 할 대상이 줄어든다. **이게 2번에서 제일 먼저 해볼 것.**

### 3번 — 판단 타당하고, 근거를 하나 더 보탤 수 있다

"확률이 정확하지 않으니 엄격하게 유지"가 맞는데, **얼마나 부정확한지**를
숫자로 말할 수 있다: K=300 부트스트랩으로 1%를 추정하면 표준오차가 약 0.6%p다.
즉 우리가 본 "1%"는 실제로는 **0.4%~1.6% 어딘가**다.

게다가 부트스트랩은 **구성 변동만** 모델링한다. 채점 환경 차이, 모델 응답의
시점 차이 같은 건 안 잡힌다. 즉 **실제 위험 > 측정된 위험**이다.

두 이유 모두 "엄격 유지"를 지지한다. 님 감각이 맞다.

### 4번 — 방향은 좋은데, **할 수 있는 것과 없는 것을 갈라야 한다**

- **못 하는 것**: AI로 프롬프트를 생성해서 테스트하기. 생성한 프롬프트에는
  **진짜 점수가 없다.** 세 모델을 실제로 돌려봐야 아는 값인데 우리에겐 그 수단이
  없다. 점수를 AI로 추정해 붙이면 그건 우리 추측을 우리가 검증하는 순환이다.
- **할 수 있는 것**: 프롬프트 없이 **숫자 분포만 합성**해서 배분기를 때리는 것.
  "비용 꼬리가 지금보다 2배 두꺼우면?", "K1 비용이 전반적으로 30% 더 비싸면?",
  "light가 유독 잘 푸는 문항 비중이 절반으로 줄면?" 같은 시나리오다.

님이 제안한 3단계 난이도(가까운 것 / 중간 / 다르지만 납득 가능한 것)는
후자에 그대로 적용하면 좋다. **부트스트랩이 "실제로 있었던 변동"만 재현하는
한계를 정확히 메우는 자리**다. 우선순위 높다.

### 5번 — 냉정하게: **이건 정보가 0이다. 하지 말자**

가중치나 규제로 조절하자는 감각은 좋은데, 그 전에 결정적인 문제가 있다.

premium이 어떤 문항에 K1을 주는 이유는 **그 문항의 예측 점수·비용이 좋아서**다.
그런데 **fast도 똑같은 예측값을 이미 보고 있다.** premium의 선택은 fast가 이미
가진 정보의 결정론적 함수일 뿐, 새로운 정보가 아니다.

"premium이 골랐다"는 신호를 특징으로 넣으면, 모델은 이미 가진 숫자를 한 번 더
받는 것이고 — ridge 입장에선 기존 특징들의 비선형 조합 하나가 추가되는 것뿐이다.
게다가 순환 의존(premium 배분 → fast 특징 → 모델 → premium 배분)이 생겨서
학습·추론 순서를 강제해야 하는 복잡도까지 따라온다.

**정보 이득 0 + 구조 복잡도 증가 = 하면 손해.** 이건 접는 게 맞다.

(만약 등급마다 **다른 예측 모델**을 쓴다면 얘기가 달라진다. 그때는 서로 다른
관점이 생기니 정보가 0이 아니다. 하지만 지금은 세 등급이 같은 head를 공유한다.)

## 실험으로 답함 (2026-08-21)

### B 반론 — 방향은 맞는데 이유가 다르고, 사실 **이미 해결된 문제**다

**먼저 수학적 사실 하나**: 절편이 있는 선형회귀에서 MSE를 최소화하면
**학습 데이터의 잔차 합이 정확히 0이 된다.** 정규방정식의 성질이다.
즉 우리는 이미 **log 공간에서는 합이 정확히 맞는** 상태다.
"합을 목적함수에 추가"하는 건 log 공간에선 **redundant**다.

**진짜 문제는 `exp()`다.** `sum(exp(예측)) ≠ exp(sum(예측))`이라, log 공간에서
합이 맞아도 실제 공간에선 안 맞는다. 그래서 사후 보정(Duan smearing 또는
배치합 보정)이 필요했던 것이고, 이건 **변환 문제이지 목적함수 문제가 아니다.**

**그리고 더 중요한 것**: 합은 **정확할 필요가 없다. 안정적이면 된다.**
v13(현재 최선)은 배치 합계를 13~35% 과대예측한다. 그런데도 최선인 이유는
`safety_ratio` 보정이 그 상수 편향을 그대로 흡수하기 때문이다. 실제로 v13의
premium 비용비율은 split이 바뀌어도 +0.6%밖에 안 움직인다.
-> **수준(level)은 보정이 처리한다. 해로운 건 불안정성뿐이다.**

**님의 과적합 걱정은 맞다. 다만 다른 이유로 맞다**: 합"만" 최적화하면
방정식 하나에 미지수가 1,760개라 **과소결정(underdetermined)**이다. 문항별
예측이 엉망이어도 합만 맞출 수 있고, 그건 다른 배치에선 전혀 안 맞는다.
그러니 sum-only는 하면 안 되는 게 맞다. 결론적으로 **B는 접는다.**

### 1번 결판 실험 결과 — 예상과 달랐다

생성 횟수별로 gain 상관을 나눠 재봤다(잡음이 병목인지 확인):

```
2회 생성 (n=1514):  corr(ax31)=-0.054   corr(axk1)=+0.316   실제 gain 표준편차=0.371
4회 생성 (n= 246):  corr(ax31)=-0.068   corr(axk1)=+0.032   실제 gain 표준편차=0.239
```

**잡음은 확실히 줄었다**(표준편차 0.371 -> 0.239, 35% 감소). 그런데
**ax31 상관은 전혀 안 좋아졌다**(-0.054 -> -0.068).

-> 해석: ax31 예측 실패의 원인은 **샘플링 잡음이 아니라 특징 자체**다.
   잡음을 35% 걷어내도 예측력이 안 생긴다는 건, 우리 266개 특징 안에
   ax31-vs-light를 가르는 정보가 정말로 없다는 뜻이다.

**단, 이 결론에는 확실한 한계가 있다**: 4회 생성 문항은 AIME 계열로 추정되는
별개 분포라 통제된 비교가 아니다(n=246으로 작기도 하다). 실제로 axk1 상관이
+0.316 -> +0.032로 무너지는데, 이건 "4회 문항이 다른 종류"라는 신호이기도 하고
**우리 axk1 신호가 어려운 문항에선 전이가 안 된다**는 경고이기도 하다.
후자라면 그 자체로 따로 볼 가치가 있다.

-> `output_tokens`만 예측하고 입력 부분은 계산해서 더하면, 예측해야 할

**결론 하나로 정리하면: 비용 예측 쪽 작업은 전부 합쳐도 최대 +0.005다.**
게다가 점수 예측이 좋아지면 비용 예측의 값어치는 더 떨어진다
(0.7703 → 0.7767, 겨우 +0.006). 개선 여지의 **96%가 점수 예측 쪽**에 있다.

이건 기존에 측정해둔 것과도 맞물린다: ax31 승격 gain의 예측 상관이 -0.05로
사실상 0이었다. 즉 헤드룸은 큰데 우리 특징 부류가 거기에 못 닿는다.

### 새 아이디어 — 비용을 평균이 아니라 상위 분위로 예측 (==님, 2026-08-22)

**착상**: 지금 cost head는 "평균적으로 얼마"를 예측한다. 대신 90분위 같은
비관적 추정을 쓰면, 폭주 가능성 있는 문항이 비싸 보여서 자연히 승격에서
밀려난다. 개별 문항 상한을 못 거는 이유가 "예측이 평균만 본다"는 데
있었으니, 예측 자체를 비관적으로 바꾸는 우회로다.

**판정: 원리는 맞는데 천장이 +0.005다.** 위 오라클 분해가 이 아이디어를
포함한 비용 계열 전체의 상한이다. 게다가 이건 점수를 얻는 장치가 아니라
안전을 사는 장치인데, 우리는 이미 초과확률 상한 0.3%에 있다. 우선순위 낮음.

**그래도 기록해두는 이유**: 이 계열에서 유일하게 근거가 확실한 게 하나 있다
(아래 input_tokens 분리). 그걸 할 때 같이 검토할 값어치는 있다.

### 왜 개별 문항 상한이 원리적으로 불가능한지 (v16에서 실측)

`fast`를 터뜨린 Dev 677번 문항:

| | light | ax31 | 배수 |
|---|---|---|---|
| 실제 | 0.161% of L | **6.506% of L** | **40.4배** |
| 우리 예측 | 0.038% of L | 0.096% of L | 2.5배 |
| 배치 전체 | — | — | 2.10배 |

문항 자체는 평범한데 **ax31이 이 프롬프트 하나에서 출력을 폭주**시켰다.
프롬프트에 신호가 없으니 예측은 정상값(2.5배)을 냈다.

개별 문항 배수 분포: 중앙 2.12배 / 95분위 12.27배 / 99분위 29.93배 / **최대 53.7배**.
반면 **배치 전체 배수는 2.10(Dev) vs 2.16(Train)으로 거의 고정**이다.

그래서 "모델별 소비 비율 상한"(= `share_ratio` + `MODEL_MULTIPLE_BOUND`)은
어느 값으로 잡아도 안 된다:

| 상한 rho | 허용 승격량 | 현재 사용 | 결과 |
|---|---|---|---|
| 3.0 (배치 기준) | 12.50% | 3.69% | 한 번도 안 걸림 |
| 40.4 (677번 차단) | 0.63% | 3.69% | 승격을 1/6로 |

**안전한 값이면 아무것도 안 막고, 막는 값이면 총량 cap보다 훨씬 가혹하다.**
개별 문항 단위에서 유효한 상한은 존재하지 않는다. 총량 cap이 답인 이유.

### 순차 처리("넘칠 것 같으면 light 몰아주기")가 불가능한 이유

두 겹으로 막혀 있다:

1. **계량기가 없다.** 컨테이너가 받는 에피소드는 `episode_id`와 `prompt`
   둘뿐이다. 실제 비용도, 정답 여부도, 누적 지출도 안 온다.
2. **순서 감사에 걸린다.** `docs/ENFORCEMENT.md`: 운영자가 ID·순서를 바꾼
   입력을 주고 선택이 달라지는지 확인한다.

다만 **이 아이디어의 알맹이는 이미 구현돼 있다** — 배치 전체를 한 번에 받으므로
순차적으로 눈치볼 필요 없이 λ 이분탐색으로 전체를 예산에 맞추고, 그래도 안 맞으면
진짜로 전부 light로 보낸다(`choice = np.zeros(...)`). 순차 방식보다 엄밀하게 낫다.

## 새 아이디어 — 모델 간 head 가중치 공유 (==님, 2026-08-22)

**착상**: 세 모델의 score head는 같은 특징에 대한 독립 회귀다. 그런데
프롬프트 평가는 **공통 도메인**이고, 세 모델이 받는 프롬프트도 동일하다.
그렇다면 프롬프트에 대한 정보가 어느 정도 섞인 가중치를 모델끼리 공유해도
되지 않나 — 다만 **아주 작은 선에서**, 그리고 **모델별 위험 정도를 반영해서**.

**나온 맥락**: v18의 안전 파라미터를 v16 모델에 갖다 썼더니 실측 점수가
+0.0078 올랐다(0.678182 / 0.666747). 그건 채택 불가였지만(premium 초과확률
상한 25.8%, 4번 중 1번 예산 초과) "다른 조합에서 온 값이 더 나을 수도 있다"는
신호였다.

**왜 말이 되는가 (측정과 맞물리는 지점)**:

지금은 "이 문제가 얼마나 어려운가"라는 **세 모델 공통 성분**을 세 번 따로
추정하면서 각자 잡음을 얹고 있다. 그리고 라우터가 실제로 쓰는 건 head의
**차이**인데:

- ax31 승격 이득의 예측 상관 = **-0.05** → ax31과 light의 head 차이는 잡음
- axk1은 진짜 신호가 있음 (`def` t=13.7, `assert` 13.4, `return` 12.3)

**공통 성분으로 수축시키면 잡음인 차이는 죽고 진짜 차이는 남는다.** 그리고
수축 강도가 모델마다 달라야 한다는 것도 여기서 나온다 — ax31은 강하게,
axk1은 약하게. ==님이 "각 모델의 위험 정도 계수도 반영해서"라고 한 것과
정확히 같은 구조다.

**구현**: 재학습 불필요. head가 이미 선형이므로 닫힌 형태로 편집된다.

    beta_m <- (1 - lam_m) * beta_m + lam_m * mean_over_models(beta)

`training/experiment_head_pooling.py`. lam을 균일/모델별로 쓸어보고,
동일 위험 상한(0.3%)에서 얻을 수 있는 최고 점수를 등급별로 비교한다.

**주의**: 수축은 차이를 줄이므로 **너무 세게 걸면 승격 자체가 사라진다**.
lam=1.0이면 세 모델의 예측 점수가 같아져서 라우터가 전부 light로 보낸다.
그러니 "작은 선에서"가 핵심이고, ax31처럼 신호가 없는 쪽만 강하게 거는
비대칭 형태가 유망하다.

## 안전 정책 확정 (==님, 2026-08-22)

**초과확률(부트스트랩 95% 상한 기준) 운용 규칙:**

| 구간 | 행동 |
|---|---|
| **1.5% 초과** | **절대 금지.** 어떤 점수 이득이 있어도 채택하지 않는다 |
| 1.0 ~ 1.5% | 상한선. 여기 근접했으면 **steady** — 더 열지 않는다 |
| 0.5% 이하 | **공격적 튜닝 허용** — 여유가 있으니 점수를 가져온다 |

근거가 되는 실측:
- 공식 `hash_regex` baseline: 예산의 98~99.6% 사용 → 초과확률 상한
  **fast 44.4% / balanced 40.9% / premium 51.8%** (리샘플마다 배분기 재실행,
  우리와 동일한 방식). 표시 점수 Dev 0.695369는 자기가 보정한 표본에서 받은
  값이고, 기댓값으로 환산하면 약 0.40이다.
- 우리 v16: 세 등급 모두 상한 0.3%, 기댓값 ≈ 0.668.

즉 "표시 점수"와 "기댓값"이 0.3 가까이 벌어질 수 있다. 이 규칙은 그 함정을
구조적으로 막는다.

현재 v16은 전 등급 0.3%이므로 **0.5% 이하 구간 = 공격적 튜닝 허용**에 해당한다.
1.0~1.5%까지는 열어볼 여지가 있다는 뜻이기도 하다 (fast의 경우 safety 0.30이
상한 4.7%라 금지, safety 0.10이 1.57%로 경계선).

## 새 아이디어 — 삼각함수 기저로 다차원 특성 확장 (==님, 2026-08-22)

**착상**: 특성을 여러 삼각함수에 통과시켜 다차원으로 확장하면, 여러 함수를
거치므로 더 안정적인 표현이 나오지 않을까. GBM 같은 트리 앙상블 없이
비선형성을 얻는 중간 경로.

**판정: 착상이 정확히 표준 기법에 대응한다.** 이건 random Fourier features
계열이다 — `x`를 `sin(w·x), cos(w·x)` 쌍으로 확장하면 선형 모델로 RBF 커널을
근사할 수 있다는 결과가 있다. 즉 **모델 구조는 선형(ridge) 그대로 두고
특징만 바꿔서 비선형을 얻는다**. GBM처럼 새 학습 알고리즘을 컨테이너에
구현할 필요가 없고, 추론은 여전히 내적 한 번이다.

**우리 맥락에서의 장단**:
- 장점: 컨테이너 제약(표준 라이브러리, 90초)에 그대로 맞는다. ridge의
  closed-form도 유지된다.
- 단점: 특징 수가 배로 늘어난다. 지금 266개인데 Train이 1760문항이라
  차원/표본 비가 이미 빠듯하다. **과적합 위험이 바로 여기서 온다.**
- 완화책: 확장 대상을 손수 만든 dense 특징 10개로만 한정하면(해시 슬롯 256개는
  제외) 증가폭이 작다. 10개 -> sin/cos 각 3주파수면 +60개.

**검증 순서**: dense 특징에만 적용 -> OOF로 alpha 재선택 -> 두 split 실측.
v17의 교훈대로 **한 번에 한 가지만** 바꾸고 `--cost-fit`은 classic 고정.

## 안전 기준 개정 — 3중 판정으로 (2026-08-22, 실측 기반)

앞서 적은 단일 기준(1.5% 하드 상한)을 실측으로 검증하고 개정한다.

### 검증 1 — "부트스트랩이 실제 변동보다 작다"는 전제는 성립하지 않았다

Train의 실제 예산비율이 Dev 부트스트랩 분포에서 몇 σ 떨어져 있는지 쟀다.
부트스트랩이 맞다면 평균 |z| ~ 1이 나와야 한다.

| 설정 | fast | balanced | premium |
|---|---|---|---|
| v16 | -0.7σ | +0.3σ | +0.4σ |
| hash_regex | -1.4σ | -1.2σ | -0.8σ |

전부 1.4σ 이내. **두 공개 split 사이에서는 부트스트랩이 변동을 과소평가하지
않는다.** 그리고 hash_regex가 위험한 진짜 이유가 여기서 드러난다 — 한도가
자기 부트스트랩 평균에서 **0.0~0.3σ** 거리다. 분포 이동 때문이 아니라 분포
한가운데를 한도로 잡은 것이다.

### 검증 2 — 0.5% 위에는 얻을 점수가 없다

SAFETY_GRID의 빈 구간(0.05~0.10)을 0.01 간격, k=3000으로 채웠다.

| safety | cap/light | 95% 상한 | 점수 |
|---|---|---|---|
| 0.05 (v16) | 1.0125 | 0.10% | 0.6118 |
| 0.07 | 1.0175 | 0.26% | 0.6144 |
| **0.08** | 1.0200 | **0.44%** | **0.6150** (최고) |
| 0.09 | 1.0225 | 1.35% | 0.6130 |
| 0.10 | 1.0250 | 1.99% | 0.6121 |

**0.5%를 넘으면 점수가 오히려 떨어진다.** 부트스트랩 점수가 초과 시 0점을
이미 반영하므로, 위험을 더 사는 순간 손해로 돌아선다. premium도 같다
(0.56에서 0.7119 최고, 0.57부터 하락).

즉 **상한을 1.5%에서 0.5%로 조여도 잃는 것이 없다.**

### 개정된 기준 (3중)

**규칙 1 — 부트스트랩 초과확률 (표집 변동을 본다)**

| 구간 | 행동 |
|---|---|
| 0.5% 초과 | 금지 |
| 0.3~0.5% | 이득이 손익분기 `Δs > p·s`를 넘을 때만 |
| 0.3% 이하 | 자유 |

손익분기 유도: 초과 시 `w·s`를 잃고 확률이 `p`이므로 `w·Δs > p·w·s`,
가중치가 약분되어 **`Δs > p·s`**. fast(s≈0.62) 기준 0.5%면 Δs > 0.0031.

**규칙 2 — σ 여유 (꼬리 모양 가정에 강건)**

> 한도가 부트스트랩 평균에서 **3σ 이상** 떨어져 있을 것.

우리 비용 분포는 꼬리가 두꺼워 정규 가정으로 확률 환산이 틀린다. σ 단위는
직접 측정되므로 그 문제를 우회한다. 관측된 split간 이동 최대가 1.4σ이니
3σ는 관측치의 2배 이상 여유다.

**규칙 3 — 스트레스 붕괴점 (분포 이동을 본다)**

> 배치 배수가 관측치의 **2배**로 이동해도 통과할 것 (`stress_test.py`).

### 현재 v16의 판정

# [MAIN TOPIC] 비공개 데이터셋은 얼마나 비합리적일 수 있는가

## 부트스트랩으로 답할 수 없는 이유

부트스트랩은 관측한 표본에서 **복원추출**한다. 즉 우리가 보고 고정한 분포 주위의
표집 잡음만 재현한다. 구성이 다른 셋에 대해서는 **정의상 아무 말도 못 한다.**

실제로 측정해보면 부트스트랩은 두 공개 split 사이 변동은 잘 잡는다
(Train 실제 비율이 Dev 부트스트랩 분포의 1.4σ 이내). 문제는 그 너머다.

## 그래서 만든 것 — `private_set_stress.py`

|---|---|---|
| 겹치지 않는 조각 | 독립 표본끼리 얼마나 벌어지나 | 복원추출이 아니라 **비복원** |

| 적대적 선택 | 최악을 모으면 | 예측이 아니라 **바닥** |

## [MAIN TOPIC 보강] 왜 비공개셋인가 — 대회가 밝힌 취지 (==님 정리)

> 실제 서비스에서는 앞으로 들어올 요청의 분포를 완벽하게 알 수 없으며, 모델
> 서빙에도 동시성·대기열·메모리 같은 용량 한계가 있습니다. 이 과제는 공개
> Train/Dev로 정책을 개발하되 별도 입력에서도 일반화하고, 정해진 비용 안에서
> 품질을 높이는 상황을 모사합니다. 예산을 넘긴 정책은 대기열 증가, 응답 시간
> 목표 위반이나 서빙 실패를 일으킬 수 있는 **운영 불가능한 구성**으로 보아 해당
> 등급을 0점 처리합니다. (README.md 발췌)

이 문장이 우리 설계 판단의 근거다. 예산 초과는 "점수를 조금 잃는 일"이 아니라
**운영 불가 판정**이다. 그래서 표시 점수 최대화가 아니라 초과 확률 관리가
목적함수가 되어야 하고, 오늘 hash_regex 실측(표시 0.695 / 기댓값 0.40)이 그
차이를 수치로 보여준다.

## 결정적 발견 — 우리 제약은 전부 "예측된 light 비용"을 통과한다

v15 이후 나는 share 제약을 "예측 비의존적 보증"이라고 설명해왔다. **부정확했다.**
정확히는 **모델별 비용 배수 예측에는 면역이지만, 문항별 light 비용 예측에는
여전히 의존한다.**

긴 프롬프트 880개 조각에서 실측:

| 조각           | 제약이 보는 값(예측)   | 실제 값      | 허용치  | 실제 비율         |
| ------------ | -------------- | --------- | ---- | ------------- |
| 무작위 880      | 1.891          | 1.897     | 2.70 | 2.7156        |
| **가장 긴 880** | **2.670 (통과)** | **5.286** | 2.70 | **5.3432 초과** |
| 가장 짧은 880    | 2.178          | 2.021     | 2.70 | 2.1252        |

무작위 조각에서는 예측과 실제가 1.891 vs 1.897로 거의 같다 — 그래서 평소에는
잘 작동한다. **구성이 치우치는 순간 예측이 절반으로 틀리고, 제약은 그걸 모른 채
통과시킨다.**

같은 이유로 cap을 조여도 안 고쳐진다 (premium safety 0.56->0.50에서 5.3432->5.3404).
cap도 예측 총합에 곱해지므로, 예측이 낮아지는 조각에서는 cap도 같이 낮아진다.

**즉 우리 방어막 전체가 단일 지점(문항별 light 비용 예측)을 통과한다.**

### 시도했다가 폐기한 해법

"cap 분모를 계산된 입력비용(문자수 기반, R^2 0.997)으로 바꾸자" — 측정으로 죽었다.
입력/실제light 비율이 구성에 따라 0.087~0.766으로 **8배** 흔들린다(현행 예측 방식은
53.5% 변동). 짧은 프롬프트는 출력이, 긴 프롬프트는 입력이 비용을 지배하기 때문.

| | 구성 전반 관측 최대 | 우리 상한 | 여유 |

- 한 번에 한 가지만 바꾼다 (v17에서 `--cost-fit`을 같이 바꿔 측정을 통째로

## k 인자에 대한 정리 (==님 질문)

`k` = 부트스트랩 반복 횟수. 매 반복마다 복원추출로 n개를 다시 뽑고 배분기를
다시 돌려 예산 초과 여부를 센다. 분해능 `1/k`, 표준오차 `sqrt(p(1-p)/k)`.

| k | 0회 관측 시 95% 상한 | premium(11/5000=0.22%) 기준 |
|---|---|---|
| 1,000 | 0.30% | — |
| 5,000 | 0.06% | **0.364%** (현재) |
| 20,000 | 0.015% | 약 0.30% |

**k를 올려도 점 추정은 안 변한다.** 몬테카를로 오차만 줄지, "공개 2640문항이
실제 분포를 대표하는가"라는 더 큰 불확실성은 못 줄인다 — 그건 스트레스 테스트의
영역이다. 최종 확정 시 k=20000으로 한 번 재는 정도가 적절.

## 새 아이디어 — 랭킹용 비용에 볼록/활성화 함수 (==님, 2026-08-23)

**착상**: 비싼 문항에 더 심한 벌점을 줘서 싼 문항 여럿을 택하게 한다. ML의
활성화함수(sigmoid, ReLU)와 결이 같다. "완전히 볼록을 씌우는 게 아니라, 볼록
씌운 값으로 보정하는 방식"도 함께 검토.

**claude 정정**: 처음에 "예산 제약은 선형이라 볼록 페널티는 참 목적함수에서
벗어난다"고 했는데, **부정확했다.** 배분기는 이미 두 비용을 분리해서 쓴다:

```
ev    = 점수 − penalty · risk · pred_rank_costs / rank_light_total   (랭킹)
total = pred_costs[...].sum()                                        (예산 검사)
```

**랭킹용에만 씌우면 예산 회계는 선형 그대로**다. 제약을 왜곡하지 않고 선호
순서만 바꾼다 — 그 단점이 사라진다.

**근거**: v20b가 이미 이 방향으로 우연히 갔고(집중도 12.8%->2.7%) 결과가 좋았다.
볼록 페널티는 그걸 의도적으로 하는 것.

`training/experiment_rank_shape.py`로 네 형태를 측정 중:
power / blend(부분 보정) / relu / sigmoid.

### 활성화함수 계열 확장 논의 (==님, 2026-08-23)

==님: "ReLU가 맞을 수도 있겠네. 그럼 Leaky ReLU, GELU도? 음수 처리 목적이
우리랑은 좀 다르려나"

**==님이 스스로 던진 의문이 핵심을 짚었다.** DNN에서 ReLU 계열의 음수 처리는
**기울기 소실/죽은 뉴런** 대응이다. 우리는 역전파가 없고 닫힌 형태의 순위
계산이라 **그 동기는 전혀 안 옮겨온다. 옮겨오는 건 모양뿐이다.**

그런데 모양만 놓고 보면 "음수 구간"이 우리 맥락에서도 명확하다:

```
relu:  c + b · max(0, c − t)
                    └─ 이 값이 음수 = 임계보다 싼 문항
```

**Leaky ReLU는 의미가 있다 -> 채택해서 실험.** 현재 relu는 싼 문항에 아무것도
안 한다(벌점 0). Leaky를 쓰면 `c < t` 구간에 작은 음의 기울기가 붙어 **싼 문항에
할인**이 들어간다. "비싼 걸 밀어내는 것"에 더해 **"싼 걸 끌어당기는 것"**이
되므로 승격을 퍼뜨리는 효과가 강해진다 — 우리 목적과 방향이 같다.

**GELU는 이미 들어가 있다 -> 추가 안 함.** GELU는 `x·Φ(x)`인 부드러운 게이트인데,
실험의 `sigmoid t=3 b=1.5`가 `c·(1 + b·S((c−t)/s))`로 기능적으로 거의 같다.
시그모이드 대신 정규분포 CDF를 쓰는 차이뿐이라 우리 스케일에서는 구분이 안 된다.

**구현 시 안전장치**:

```python
np.maximum(c * 0.05, c + b * np.where(c >= t, c - t, a * (c - t)))
```

할인이 들어가면 아주 싼 문항의 비용이 0이나 음수가 될 수 있고, 그러면 라우터가
"공짜"로 인식해 λ 이분탐색이 깨진다. 원래 비용의 5%를 바닥으로 뒀다.
**DNN에서는 음수 출력이 정상이지만 여기서는 비용이라 부호가 의미를 갖는다**는
것이 결정적 차이.

### 랭킹 변형 실험의 판정 기준 (측정 전 고정)

기준선은 v20b의 부트스트랩 가중합.

| 결과 | 판정 |
|---|---|
| 가중합 +0.003 이상 **그리고** 상한 0.5% 이하 | 채택 검토 (전체 재보정 필요) |
| +0.001 ~ +0.003 | 집중도가 크게 좋아진 경우만 검토 |
| 그 미만 | **기각**, v20b 그대로 병합 |

집중도(최악 1건의 초과분 비중)를 함께 보는 이유: 점수로는 안 잡히는 이득이기
때문이다. v20b가 12.8% -> 2.7%로 낮춘 것이 실제로 구성편향 시나리오 통과로
이어졌다.
