# v22d — 해시 슬롯에서 길이를 분리하고, 산 점수만큼 여유를 되돌린다

브랜치: `SmartRouter-v22` (base: `SmartRouter-v21`)

**제출본입니다.** 공식 self-check 최악 split **0.665199**, k=5000 감사 최악
등급 95% 상한 **0.095%**, 폭주 시나리오에서 총점이 0이 되는 설정 **없음**.

## 배경

v21d는 최악 split 0.660384였고, 채택 근거는 점수가 아니라 폭주 내성이었다
(v20b는 세 등급이 동시에 넘는 설정을 하나 가지고 있었다). 남은 개선 여지는
오라클 분해가 이미 말해줬다 — 격차 0.0893 중 0.0662가 점수 예측에 있고
비용 예측은 완벽해도 −0.0041이다. 그래서 이번에는 특징 쪽을 건드렸다.

## 발견 1 — 해시 슬롯이 길이를 두 번 세고 있었다

256개 FNV-1a 해시 슬롯은 "어떤 단어가 나왔나"를 담으라고 만든 것이다.
그런데 정규화가 없으면 **프롬프트가 길수록 모든 칸이 통째로 커진다.** 길이는
이미 dense 특징 10개에 들어 있으므로, 모델은 같은 정보를 해시 슬롯에서 다시
배우면서 정작 단어 구성은 덜 배우게 된다.

**대응**: 슬롯을 L1 정규화하고, 정규화하며 버린 총량을 `log1p(합)` 한 칸으로
되살린다. 버리는 게 아니라 **크기와 방향을 분리**하는 것이다.

```python
total = _team_math.fsum(abs(v) for v in vector[offset:])
if total > 0.0:
    for i in range(offset, offset + hash_bins):
        vector[i] /= total
vector.append(_team_math.log1p(total))
```

특징 326 → 327. `feature_version`을 `team-features-v2`로 올렸다.

## 발견 2 — 비용 예측이 실제로 좋아졌고, 탐색이 그걸 전부 써버렸다

재탐색이 고른 fast는 safety **0.70**이었다. v21d는 0.15다. 의심스러워서
확인했더니 사실이었다 — v21d의 예측기로 fast를 safety 0.60까지 밀면
부트스트랩 1000회 중 **395회** 초과하는데, v22의 예측기에서는 safety를
**1.00까지 밀어도 [0, 0]** 이다. k=5000 감사도 fast 0/5000을 확인했다.

| | v21d | v22 |
|---|---|---|
| fast safety 0.60~0.70의 초과 (k=1000) | 395/1000 | **0/1000** |
| k=5000 감사 fast | — | **0/5000, 상한 0.060%** |

**여기까지는 순수한 이득이다.** 가중 점수가 0.6604 → 0.6772로 +0.0168.

문제는 그 다음이다. 감사는 **"이 배치의 비용이 다시 뽑혀도 통과하는가"**를
묻는다. **"비공개셋이 그냥 더 비싸면 어떻게 되는가"**는 묻지 않는다.

## 발견 3 — 그 질문을 하는 시험이 자동 실행에서 빠져 있었다

스트레스 도구는 둘이다.

- `private_set_stress.py` — **어떤 문항이** 배치에 들어오는가가 달라지면?
- `stress_scenarios.py` — **같은 문항이** 예상보다 비싸면?

`finish_arm.sh`는 첫 번째만 돌리고 있었다. 그런데 v21d를 v20b 대신 고른
근거가 **두 번째**다. 손으로 돌려보니:

| 배치 전체 비용배수 | v21d 초과 등급 | v22 초과 등급 |
|---|---|---|
| 3.0배 (dev) | 1개 | **0개** |
| 4.0배 (dev) | 2개 | **3개 = 총점 0** |
| 6.0배 (dev) | 2개 | 3개 = 총점 0 |
| 6.0배 (train) | 2개 | 3개 = 총점 0 |
| 합계 | 9칸 | 11칸 |

v22는 3배까지 **오히려 더 잘 버틴다.** 그런데 4배에서 세 등급이 동시에
무너진다. 한 등급이 넘으면 그 등급만 0점이지만, 세 등급이 동시에 넘으면
총점이 0이다.

원인은 기준 예산비율에 그대로 보인다. v22 fast는 한도 1.25에 **1.1442**,
v21d는 1.0523이다. **점수를 여유로 샀다.**

## 대응 — fast만 조인다

4배와 6배를 둘 다 견디는 최대 safety를 찾았다.

| safety | fast 점수 | dev@4배 | dev@6배 | 4배 | 6배 |
|---|---|---|---|---|---|
| 0.70 (탐색이 고른 값) | 0.6556 | 1.3610 | 1.5894 | 초과 | 초과 |
| 0.30 | 0.6403 | 1.2036 | 1.3308 | 통과 | 초과 |
| 0.25 | 0.6379 | 1.1694 | 1.2751 | 통과 | 초과 |
| **0.20 (채택)** | **0.6358** | **1.1312** | **1.2127** | **통과** | **통과** |

가중 −0.0079를 내고 총점 0 시나리오를 전부 없앴다. balanced와 premium은
탐색이 고른 값을 그대로 쓴다.

## 도구 변화

1. **`finish_arm.sh`가 스트레스 도구를 둘 다 돌린다.** 그리고 "총점 0
   시나리오 N개"를 직접 찍는다. 이번 건을 손으로 찾아야 했던 이유가
   그 줄이 없었기 때문이다.
2. **`check_pick_monotone.py` 신설.** 예산을 덜 쓰는 지점이 더 자주 초과했다면
   그 사이의 0은 잡음이다. 감사가 3분 걸려 내리는 판정을 곡선 모양만으로
   즉시 내린다 (다음 절 참조).
3. **`stress_scenarios.py --params`** — 구워진 아티팩트 말고 탐색 결과
   파일에서도 파라미터를 읽는다. 두 arm을 브랜치 전환 없이 나란히 비교할 수
   있게 하려는 것이고, 그게 안 되면 표에 엉뚱한 숫자가 섞인다.
4. **행렬을 더는 커밋하지 않는다.** Colab 노트북이 `export_matrices.py`로
   직접 만든다. 재생성본이 커밋본과 배열 단위로 동일함을 확인했다.

## 다음 arm(v23)에서 확인된 것

v23은 승격 사건을 별도 분류기로 배워 ax31 헤드에 섞는 시도였고, **기각**했다.
자세한 내용은 브랜치 `SmartRouter-v23`의 커밋 메시지에 있다. 요약:

- 부트스트랩 +0.0082, 실제 **−0.0035**
- 등급별 부호가 갈렸다. ax31을 주력으로 쓰는 balanced에서 손해고, ax31 승격이
  거의 없는 fast에서만 이득이다
- **부호를 배웠는데 배분기는 크기로 순위를 매긴다.** 이 축은 분류가 아니라
  순위 학습으로 접근해야 한다

그리고 v23에서 **k=5000 감사가 처음으로 보정된 운용점을 거부했다** —
premium 26/5000, 95% 상한 0.721%(목표 0.3%). 곡선을 보면 이유가 보인다.

| safety | v22d premium | v23 premium |
|---|---|---|
| 0.25 | [0, 0] | **[1, 0]** |
| 0.30 (둘 다 선택) | [0, 0] | [0, 0] |
| 0.40 | [13, 0] | [23, 0] |

예산을 덜 쓰는데 더 자주 넘길 수는 없으므로, 0.25에서 1회가 관측됐는데
0.30에서 0회라면 **그 0은 잡음이다.** 그리고 점수를 최대화하는 선택기는
구조적으로 그런 웅덩이에 빠진다 — 웅덩이가 바로 높은 점수와 낮은 측정
초과율이 만나는 곳이다. 이 관찰이 `check_pick_monotone.py`가 됐다.

## 재현

`--cost-fit`은 `classic`(단일 log-MSE alpha + Duan smearing)이 출하 경로다.

```
# 1) 학습 -> training/artifact.json
#    주의: 이 단계는 계수만 만든다. 안전계수/위험계수는 4번의 apply_search가
#    나중에 덮어쓰므로, 여기서 멈추면 아티팩트는 아직 운용 가능한 상태가 아니다.
python training/train_router.py \
    --train-input data/materialized/train/inputs.json \
    --train-outcomes data/train/outcomes.json \
    --cost-fit classic --out training/artifact.json

# 2) 탐색용 행렬 (커밋되어 있지 않다; 여기서 만든다)
python training/export_matrices.py --artifact training/artifact.json \
    --out build/search-matrices.npz

# 3) 안전계수 탐색 -- 등급 x risk_high 로 6조각까지 나눌 수 있다
#    파일명이 build/v22-curve-sN.json 이어야 4번이 찾는다
python training/search_standalone.py --matrices build/search-matrices.npz \
    --tiers fast --risk-high 1.0 1.5 2.0 2.5 --workers 2 \
    --out build/v22-out-s1.json --curve-out build/v22-curve-s1.json

# 4) 6조각이 모이면 나머지를 한 번에
#    보정 -> 단조성 점검 -> k=5000 감사 -> 굽기 -> self-check
#    -> 구성 스트레스 -> 폭주 시나리오
bash training/finish_arm.sh v22 build/search-matrices.npz
```

`notebooks/v22-s*.ipynb` 는 3번을 Colab 6계정에 나눠 돌리는 형태다. 각 조각은
저장소를 clone하고 행렬을 직접 만든 뒤, 결과 곡선을 gzip+base64 블롭으로
찍는다. `training/restore_colab_curves.py` 가 그 블롭을 되돌리며 조합 수,
헤더가 광고한 SHA-256, 조각 ID 중복을 검사한다.
