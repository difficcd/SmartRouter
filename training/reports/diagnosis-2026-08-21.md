# 진단 리포트 — 어디에 진짜 개선 여지가 있는가 (2026-08-21)

v1~v8이 총 +0.0017을 얻는 데 그쳤다. "왜 이렇게 미미한가"를 파기 위해 실측
진단을 돌렸고, 개별 튜닝보다 훨씬 큰 구조적 문제 세 가지를 찾았다. 이 문서는
그 근거 숫자를 남긴다.

## 1. ax31 승격 판단에 예측력이 없다 (상관계수 -0.05)

라우팅 결정에 실제로 쓰이는 건 절대 점수가 아니라 **모델 간 점수 차이(gain)**다.
out-of-fold 예측 gain과 실제 gain의 상관계수:

| alpha | corr(ax31 - light) | corr(axk1 - light) |
|---:|---:|---:|
| 100 | **-0.074** | +0.232 |
| 1000 (현재) | **-0.052** | +0.300 |
| 10000 | **-0.054** | +0.247 |

**`ax31` 승격은 사실상 무작위 선택이다.** fast(58개)·balanced(809개)가 하는
일의 거의 전부가 ax31 승격인데 예측력이 0(오히려 음수)이다. `axk1`은 +0.30으로
약하지만 실재하는 신호가 있다.

### gain을 직접 학습하면? -> 수학적으로 동일

"각 모델 점수를 따로 예측하고 빼는" 대신 gain을 타깃으로 직접 학습해봤다.
결과가 소수점까지 완전히 같았다 — ridge는 선형 연산자라
`coef(y2 - y1) = coef(y2) - coef(y1)`이 항상 성립하기 때문이다.

**즉 학습 방식의 문제가 아니라, 266개 특징 안에 ax31-vs-light를 가르는 신호가
없다는 뜻이다.** 표면적 특징(길이, 기호 수, 단어 해시)의 한계.

## 2. 비용 예측이 배치 합계 기준으로 크게 부풀려져 있었다

v1이 넣은 Duan smearing은 **문항별 기댓값**을 불편추정하도록 보정한다. 그런데
라우터의 `cap`도, 공식 채점의 예산 검사도 **배치 합계**만 본다. 실측:

| 모델 | smearing 계수 | Train 배치합 예측/실제 |
|---|---:|---:|
| ax31-light | 1.6476 | **1.3518** |
| ax31 | 1.4550 | **1.2356** |
| axk1-think | 1.8398 | **1.1343** |

배치 합계를 24~35% 과대예측하고 있었고, 모델마다 편차도 달랐다. 이 때문에
안전계수를 과도하게 조여야 했다.

### 결과: fast는 허용 예산의 1/10만 쓰고 있었다

`cap = light_total × max(1.0, budget_multiplier × safety_ratio)`.
fast는 `1.25 × 0.82 = 1.025` — **허용된 25% 여유 중 실제로 2.5%만 사용.**
안전계수가 "여유분"이 아니라 "배수 전체"에 곱해지는 구조라 이렇게 된다.

-> v9에서 보정 기준을 "out-of-fold 예측 합 = 실제 합"으로 바꿈.

## 3. alpha를 잘못된 공간에서 골랐다

log-cost의 MSE로 alpha를 골랐지만, 예산 검사는 **실제(exp) 스케일**에서 일어난다.
배치 보정 후 실제 스케일 기준으로 재측정:

| alpha | light | ax31 | axk1 | 실제스케일 MSE |
|---:|---:|---:|---:|---:|
| 1000 (log-MSE 최적) | 0.559 | 0.604 | 0.175 | 2.176e-02 |
| 10000 | **0.617** | **0.654** | **0.216** | **1.797e-02** |
| 100000 | 0.624 | 0.660 | 0.212 | 1.744e-02 |

**우리가 최적화한 지표(log MSE)와 실제로 필요한 지표(실제 스케일 정확도)가
달랐다.** -> v10에서 `select_cost_alpha`로 실제 스케일에서 선택하도록 변경.

## 4. fast의 이론적 천장 측정

같은 예산에서 승격 순위를 어떻게 매기느냐에 따른 실제 Dev 점수
(예산 회계는 실제 비용 기준 = 비용을 완벽히 안다고 가정):

| 순위 기준 | fast | balanced |
|---|---:|---:|
| gain/cost (현재 방식) | **0.6634** (402개) | 0.6906 (866개) |
| gain만 (비용 무시) | 0.6349 (154개) | 0.6940 (867개) |
| 완전 무작위 | 0.6415 (231개) | 0.6872 (790개) |
| **우리 라우터 실제** | **0.6278** (58개) | 0.6906 (809개) |

**fast의 격차 +0.0356은 "이득 예측"이 아니라 "비용 불확실성 때문에 예산을 못
쓰는 것"에서 온다.** 지금까지 8개 버전으로 얻은 총 개선의 20배 규모.

## 5. 시도했지만 아니었던 것들 (기록)

- **문항별 비용 상한(꼬리 제거)**: 예측 상위 5%/20% 고비용 문항을 승격 후보에서
  제외 -> 초과율이 오히려 비슷하거나 악화. 우리 비용 예측이 부정확해서 "진짜
  비싼 문항"을 식별하지 못하는 게 원인.
- **안전계수를 더 공격적으로**: 기댓값(초과 시 등급 0점 반영)으로 계산하면
  현재 선택이 이미 최적이었다.
  `0.82: 0.99×0.6278=0.6215` / `0.88: 0.92×0.6425=0.5911` / `0.94: 0.74×0.6559=0.4854`
- **TTR(어휘 다양성), 문장당 단어수**: 놓친 문항 식별용 특징으로 검증했으나
  구분력 없음(놓친 0.646 vs 나머지 0.634 / 9.54 vs 10.35).
- **임베딩**: 필요한 건 문장 임베딩(문항 유형 판단)인데 컨테이너가 네트워크
  차단 + 표준 라이브러리만 허용이라 실행 자체가 불가능. 구울 수 있는 형태(단어
  임베딩 조회 테이블)는 지금 해시 특징과 구조가 같아 이 문제를 못 고침.

## 6. 선택 편향(winner's curse) 확인

배치 보정 후 fast에서 한 번 배분해보고 측정:

```
전체 880문항:    예측합/실제합 = 0.984   <- 배치 보정 성공
승격된 346개만:  예측합/실제합 = 0.793   <- 21% 과소예측
```

라우터는 gain/cost로 순위를 매기므로 **비용이 과소예측된 문항을 우선적으로
고른다.** 전체 평균이 맞아도 선택된 부분집합에서는 틀린다 — 배치 보정만으로
안전계수가 크게 안 풀린 이유.
