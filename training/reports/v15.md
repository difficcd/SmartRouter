# v15 — safety_ratio 재정의 + 점유율 기반 경성 예산 제약

브랜치: `SmartRouter-v14` (base: `main` @ v13)
(브랜치 이름은 v14에서 시작했으나 v14의 목표가 v15에 흡수되어 한 번에 검증한다)

## 배경: 안전장치들이 전부 같은 가정 위에 있었다

v13까지의 안전장치 세 개는 모두 **문항별 비용 예측**에 의존한다:

| 장치 | 무엇에 의존하나 |
|---|---|
| `safety_ratio` | 예측 비용 합으로 계산한 `cap` |
| `risk_multiplier` | 예측 비용에 곱하는 배수 |
| `high_cap_ratio` | 예측 비용으로 잰 axk1 몫 |

그런데 그 예측의 실제스케일 상관은 **0.46~0.62**에 불과하다. 즉 예측이
크게 빗나가는 상황에서는 **세 장치가 함께 무력해진다** -- 상관된 실패다.
이건 정확히 `hash_regex`가 죽은 방식이기도 하다.

## 변경 1 — `safety_ratio`를 "허용 여유분의 비율"로 재정의

```
이전: cap = light_total * max(1.0, budget_multiplier * safety_ratio)
이후: cap = light_total * (1 + (budget_multiplier - 1) * safety_ratio)
```

이전 형태에서는 같은 `safety_ratio`가 등급마다 전혀 다른 뜻이었다.
premium(4.0배)에서 0.7은 2.8배를 허용하지만, fast(1.25배)에서 0.7은
`max(1.0, ...)` 바닥에 걸려 **승격을 아예 못 한다.** fast는 0.80 미만이
전부 같은 죽은 값이었고, 탐색이 계속 고르던 0.84조차 허용된 25% 중
**5%만** 쓰는 값이었다.

새 형태에서는 "이 등급이 all-light 위로 쓸 수 있는 몫 중 몇 %를 쓸까"로
의미가 통일되고, fast도 다른 등급과 같은 탐색 해상도를 갖는다.

**부수 사고와 수정**: 재정의 직후 fast의 초과율이 3%(목표 1%)로 튀었다.
새 그리드를 0.30부터 시작하게 짜는 바람에 fast의 안전 구간(0.05~0.25,
cap 1.01~1.06)이 그리드 밖으로 밀려난 것이다. 0.05~0.25를 추가해 해결했다.
점수만 봤다면 v13보다 높아 보여 그대로 채택했을 사고였다 -- `overrun`을
같이 보는 습관이 잡아냈다.

## 변경 2 — 점유율 기반 경성 제약 (핵심)

예산 검사를 다시 쓰면
```
비용비율 = 1 + Σ_promoted (c_m(i) - c_light(i)) / L
        = 1 + Σ_m (ρ_m - 1) · s_m
```
`s_m`은 m으로 승격된 문항들이 차지하는 **light 비용 점유율**,
`ρ_m`은 그 모델의 **배치 수준 비용배수**다.

이 형태가 값진 이유는 두 항의 신뢰도가 완전히 다르기 때문이다:

| | 실측 |
|---|---|
| 문항별 비용 예측 | 실제스케일 상관 **0.46~0.62** |
| 배치 수준 배수 ρ | ax31 2.1020 -> 2.1550 (**+2.5%**), axk1 23.795 -> 23.150 (**+2.7%**) |

그래서 ρ에 넉넉한 상한(`ax31 3.0`, `axk1 33.0` -- 관측보다 약 40% 위)을
두고 제약을 건다:
```
Σ_m (ρ_m^상한 - 1) · s_m  ≤  (budget_multiplier - 1) · share_ratio
```
`share_ratio`는 부트스트랩으로 탐색하되 **점수를 잃지 않는 선에서 가장
강한 값**을 고른다(`SCORE_TOLERANCE` 이내). 1.0이면 제약 없음이므로
최악의 경우에도 기존 동작과 같다.

### 이 제약의 정확한 성질 (과장하지 않기)

- **수준(level) 독립적이다**: `s_m`이 정규화된 점유율이라, 예측 light 비용의
  전체 수준이 틀려도 상쇄된다.
- **완전한 예측 독립은 아니다**: 문항 간 상대 비중이 틀리면 `s_m`도 틀린다.
  기존 장치들보다 훨씬 견고하지만 수학적 보장은 아니다.
- **선택 편향은 이번엔 유리하게 작동한다**: 우리는 `gain/cost`로 순위를
  매기므로 ρ가 배치 평균보다 **낮은** 문항을 우선 고른다. 배치 평균을
  상한으로 쓰는 것이 그만큼 보수적으로 작동한다.
- **상한 자체는 관측 2개에서 나왔다**: 40% 여유를 뒀지만 근거가 두껍진 않다.

## 배선

탐색기(`search_standalone.py`)뿐 아니라 **실제 라우터(`heuristic.py`)까지**
연결했다. 처음엔 탐색기에만 넣어서, 좋은 `share_ratio`를 찾아도 제출되는
라우터는 제약을 무시하는 상태였다 -- v13에서 `high_cap_ratio`가 한 번도
발동하지 않았던 것과 같은 종류의 구멍이었다.

## 탐색 결과 (부트스트랩)

| 등급 | safety | high_cap | **share** | 최악 초과율 | 점수 |
|---|---:|---:|---:|---:|---:|
| fast | 0.15 | 1.00 | **0.90** | 0.003 | 0.6199 |
| balanced | 0.70 | 1.00 | 1.00 | 0.000 | 0.6881 |
| premium | 0.55 | 1.00 | 1.00 | 0.003 | 0.7138 |

**점유율 제약이 fast에서만 발동했다(0.90).** 의도한 대로다 -- fast는 여유가
25%뿐이라 가장 위험하고, balanced/premium은 이미 충분해서 제약이 무의미하다.

## 실측 결과 (공식 self-check, 두 split)

| | Dev | Train | **최악** |
|---|---:|---:|---:|
| v13 (현재 main) | **0.674148** | 0.663409 | 0.6634 |
| v15 | 0.673580 | **0.664006** | **0.6640** |

점수는 사실상 무승부다(최악 기준 +0.0006).

**그런데 안전 여유가 나빠졌다:**

| 등급 | v13 (여유 / split간 변동 / 배수) | v15 |
|---|---|---|
| fast | 14.1% / 5.4% / **2.6배** | 13.3% / 5.8% / **2.3배** |
| balanced | 14.9% / 3.1% / **5.6배** | 14.7% / 1.6% / **9.1배** |
| premium | 60.8% / 0.6% / **101배** | 38.8% / 6.0% / **6.4배** |

premium이 101배 -> 6.4배로 급락했다. 재파라미터화로 탐색 공간이 넓어지자
탐색기가 premium에서 예산을 더 쓰는 쪽(비용비율 2.487 -> 2.718)을 골랐고,
split 간 변동도 0.6% -> 6.0%로 10배 커졌다.

## 판정: 채택하지 않는다

**점수 이득 없이 안전 여유만 내준 거래다.**

부트스트랩은 두 버전 모두 "초과율 1% 이하"라고 말한다. 하지만 부트스트랩은
**split 내부 재표본만** 모델링한다 -- hash_regex를 죽인 건 split *간* 이동이었고,
그 지표로 보면 v15가 명백히 나쁘다. 두 지표가 엇갈릴 때는 일반화를 직접
겨냥하는 쪽을 믿는다.

`main`은 v13을 유지한다.

## 그래도 남는 것

**코드는 유효하다.** 재파라미터화도 점유율 제약도 구조적으로 옳고,
`heuristic.py`까지 배선돼 있다. 문제는 제약이 아니라, 탐색기가 "안전한 것 중
점수 최대"를 고르다 여유를 다 써버린 것이다.

-> **다음 시도**: `OVERRUN_TARGET`을 1% -> 0.5%로 조이고 재탐색하면, 같은
   코드로 v13 수준의 여유를 되찾으면서 재파라미터화 이득만 챙길 수 있다.

## 부수 성과

`verify_both_splits.py`가 이제 **여유를 "관측된 split간 변동의 몇 배"로**
환산해 출력한다. 점수만 보고 채택하는 실수를 구조적으로 막는 장치이고,
이번 판정이 정확히 그것으로 이뤄졌다. 참고로 hash_regex는 0.07배였다.
